# 多机多卡 GRPO：一台训练机 + 若干台推理机

GRPO 的一步分两半：采样和打分（推理），以及在采样上更新 LoRA（训练）。2B 时这两半能挤在一张卡上；9B 不行：训练 9B LoRA 要 19–25 GB 显存，vLLM 挂 9B 底座加 critic、满意度、拒答和策略四个 LoRA 也要占满一张 32 GB 的卡。所以 9B 的 GRPO 拆到多台机器上跑。

## 有哪几种布局

| 布局 | 什么时候用 | 怎么分工 |
|---|---|---|
| 单卡 | 2B 策略 + 2B 打分模型 | vLLM（约 35% 显存）和训练同在一张卡 |
| 单机双卡 | 有双卡机器时，2×2 的任意组合 | 训练独占 GPU0；9B 的服务放 GPU1，2B 策略的采样服务留在 GPU0（`run_r3full.sh` 按策略 / 打分模型大小自动选） |
| 一台训练机 + 一台推理机 | 抢不到双卡，只有单卡机器 | 训练机只训练；推理机跑 vLLM（策略采样 + 全部打分）和 LoRA 同步服务 |
| 一台训练机 + 多台推理机 | 推理成了瓶颈 | 同上，采样和打分按提示分摊到每台推理机，每步的 LoRA 推给每一台 |

## 多机模式怎么转

```
训练机（GPU：只训练 LoRA）                         推理机 ×N（GPU：vLLM）
  ┌─────────────────────────┐   采样请求（按提示分摊）   ┌─────────────────────────────────────┐
  │ train.ans_grpo          │ ───────────────────────▶ │ :6006 vLLM：底座 + critic / sat /      │
  │  - 子进程：发采样、打分请求│ ◀─────────────────────── │        refuse / policy_v* LoRA       │
  │  - 主进程：前缀共享训练    │   回答 + 逐句打分         │ :6008 lora_sync：收 LoRA → 内存盘 → 热加载 │
  │  - 后台线程：推送新 LoRA  │ ───────────────────────▶ │                                     │
  └─────────────────────────┘   每步 LoRA（推给每一台）   └─────────────────────────────────────┘
```

- **通信**：机器之间经平台给每台实例的对外域名访问（容器内网跨宿主机不通），所有接口都要带同一把 API 密钥。实测域名带宽约 78 MB/s，每次请求多约 30 ms，所以同一提示的几条参考 logprob 合成一个请求发。
- **推送 LoRA**：训练主线程只把 LoRA 存到本机内存盘（约 0.2 秒），上传、热加载、卸载旧版本都在后台线程做。新版本在所有推理机上加载成功后，采样才切到它，所以采样最多比训练晚一步。推送失败会在下一步直接报错停下，不会悄悄沿用旧版本。
- **分摊**：`RM_URL` 和 `LORA_SYNC_URL` 都可以写成逗号分隔的列表，顺序一一对应。采样按提示轮流发给各台推理机，打分请求也分摊开；每台推理机的 LoRA 推给它自己的同步服务。
- **续训**：训练每 50 步存一次完整状态（LoRA、优化器、奖励统计、提示位置、随机数）。中途换推理机的台数、或者训练机出错，都从最近的存档接着训；推理机上已有的同名 LoRA 版本会先卸载再加载。

## 实测：瓶颈在推理

9B 策略 × 9B 打分模型，一台训练机 + 一台推理机，每步 16 个提示 × 16 条回答：

| | 耗时 |
|---|---|
| 采样 | 约 37 秒 |
| 打分（critic、满意度、拒答） | 约 12 秒 |
| 训练 | 约 27 秒 |
| 每步合计（采样、打分和训练流水线重叠） | 约 50 秒 |

推理机 GPU 一直在 95–100%，训练机每步约一半时间空等。推理机的负担主要是长输入：打分要把原文和回答整段读一遍，vLLM 处理输入约每秒 1 万 token，生成只有每秒几百 token；Qwen3.5 的线性注意力层让前缀缓存只能命中约六成，重复的原文省不掉多少。所以加一台推理机，把采样和打分分摊开，是最直接的提速办法；预期每步降到训练本身的 27–30 秒。

## 怎么启动

文件都在共享盘 `runs/pair/<配对名>/`：

| 文件 | 谁写 | 作用 |
|---|---|---|
| `key` | 第一台推理机 | API 密钥（只有自己的实例能读共享盘）；其余推理机复制同一把 |
| `loras` | 任务脚本 | 推理机要挂的 LoRA，每行「名字=路径」 |
| `domains.json` | 本地 `scripts/pair_setup.py` | 推理机的对外域名（只有平台接口查得到，容器里拿不到） |
| `infer_ready` / `infer_failed` | 推理机 | 服务起好 / 起不来 |
| `extra_pairs` | 人 | 训练机额外要连的推理机配对名，每行一个 |
| `train_done` / `train_failed` | 训练机 | 推理机看到 `train_done` 才收尾；训练失败时推理机留着，改好直接重跑训练机 |

步骤：
1. 推理机：`run_infer_node.sh`（`INFER_MODEL=qwen3.5-9b` 用 9B 底座）。9B 对照里由队列任务 `pair_infer` 启动；第二台起用 bootstrap 角色 `q9binf2`（复制同一把密钥和 LoRA 清单）。
2. 本地：`python -m scripts.pair_setup --pair <配对名> --infer_uuid <推理机实例> --via <任一台实例的登录信息>`，写 `domains.json`。
3. 有多台推理机时，在第一台的配对目录写 `extra_pairs`。
4. 训练机：`run_train_node.sh`（队列任务 `pair_train`），等所有推理机就绪、检查密钥一致和服务可达，再跑训练。

## 踩过的坑

- **9B 的 LoRA 参数名对不上，等于从零起训。** Qwen3.5-9B 的 LoRA 是按视觉语言结构保存的，参数名带 `language_model`；按纯文本 CausalLM 加载时 496 个参数一个都没加载上，PEFT 只打一条警告。训练照样能跑，奖励却往下掉、回答变长。现在 9B 走 `load_policy`，并且加载起点时只要报缺参数就直接报错退出。
- **推送的 LoRA 带视觉塔参数，vLLM 拒绝加载。** 按视觉语言结构加载时 PEFT 也给视觉塔挂了 LoRA；推送前先删掉（同 `scripts/strip_visual_lora.py`）。
- **残留进程占显存。** 停训练时评测阶段的 vLLM 子进程（`VLLM::EngineCore`）没退出，占了 29 GB；重启前要按 GPU 上的进程逐个清干净。
- **队列里的垫底任务趁空抢机器。** 训练任务一失败，队列调度马上领下一个能做的任务。重启训练前先把垫底任务占住，再放开训练任务。
- **存档间隔决定能不能随时切换。** 中途加推理机只能从存档接着训，存档间隔太长，切换要么等、要么丢进度；多机长任务的存档间隔宜设短一些。
- **不要改正在执行的 bash 脚本。** bash 边执行边读文件，中途改会读错位置；新逻辑放新文件，或等它停了再改。代码同步用 `rsync -c` 只替换真正变了的文件。

代码：`train/ans_grpo.py`（`AsyncPusher`、多服务分摊）、`train/gen_grpo.py`（`Server`、`lora_sync_url`、`strip_visual_inplace`、`load_adapters_strict`）、`scripts/lora_sync.py`、`scripts/pair_setup.py`、`scripts/remote/run_infer_node.sh`、`run_train_node.sh`、`run_r3full.sh`、`bootstrap_fs.sh`。
