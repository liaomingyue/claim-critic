# RAG 幻觉 critic：盲区驱动的迭代优化

2026-11-09 · 在线版：https://claude.ai/artifact/CzjFY2SQcd74zv5Tce4mQe

## 一句话

我做了一个逐句检测 RAG 幻觉的 critic，并把它和 RAG 生成模型放进同一个闭环里互相迭代。最重要的收获是：**critic 变不好，不是数据不够，而是不知道它在哪儿看不见。** 只补 581 条「critic 拿不准、且经人工核实为真错」的样本，AUC 就涨了 0.029；而随机加的几千条合成样本几乎没有作用。

- 时间：2026 年 10 月下旬到 11 月上旬，约两周。
- 资源：全部模型是 MiniCPM5-2B + LoRA，基本在单张 RTX 5090 上跑；人工标注用 Claude 代替，预算很紧。
- 我的角色：问题定义、方案和实验设计、每一步的判断和取舍；工程实现大量借助 AI 编程助手（Claude Code）完成。
- 主要结果：RAG 回答里含明显错误的比例从 25.2% 降到 4.7%（闭环每转一圈都在降）；critic 在人工金标上的 AUC 从 0.843 到 0.872。

## 问题：细微的错最难抓，而且模型会主动往那里钻

RAG 回答里最麻烦的幻觉，往往不是整句编造，而是一个小地方不对：原文说“有些人”，回答写成“大多数人”；原文说 A 做了某事，回答安到 B 头上。我的逐句 critic 在 Claude 标的 179 句显然错里漏了 99 句，“范围偏移”这一类只能召回三成左右。

更麻烦的是，一旦把 critic 当成 RAG 的奖励，RAG 模型会主动往它看不见的地方钻。我们实际观察到：换上一个更好的 critic 接着训，模型开始写更长的句子和列表句，因为那恰好是 critic 最弱的地方。

常见的做法都试过，也都卡住了：

- **用人工标注训 critic**：RAGTruth 原版人工标注漏标很多，训出来的 critic 学会了“不敢报错”，明显错只认出 27%。拿它当奖励，RAG 模型就什么题都硬答。
- **多造合成错误**：生成器最爱造的错（加一句空泛评价、加一个原文没有的细节）恰好是 critic 最拿手的，在它的漏判里只占 1%。从几百对加到 6000 对，没有任何提升。
- **换更强的 critic**：静态指标更好不等于 RL 后更好。三档 critic 里，AUC 居中的那档训完反而最差。

所以我把问题重新定义成：**先找到 critic 在哪类错误上看不见，再有针对地补。**

## 整体方案：以 critic 盲区为中心的闭环

```
用 critic 当奖励训 RAG（句子级奖励，从上一轮模型接着训）
  → 按类型找盲区（RAG 出错 × critic 漏判，两边都差的类型优先）
  → 定向造难样本（门槛：是真错、读着自然；难度：critic 0.3–0.5 最高）
  → 人工核实（现在由 Claude 代替；只在样本进 critic 前一次）
  → critic 重训（只补拿不准且核实过的；按类型复查召回）
  → 新 critic 再去训上一轮的 RAG 模型
```

每一轮从分析 critic 在哪类错误上看不见开始，只针对这些类型造样本。人只出现在样本进 critic 之前的核实这一步；新 critic 接着用来训上一轮的 RAG 模型。

## 关键取舍

下面是影响最大的六个决定。每个都有过别的选项，放弃它们都有实验依据。

**1. critic 的数据底座：用自己模型的回答，不用公开人工标注。** 让 2B 模型自己写回答，再让 Claude 逐句改对并标注，作为唯一的起始数据集。这样错误分布和真正要检测的模型一致。对照过纯人工和纯合成：纯合成 AUC 低 0.034（显著），纯人工当奖励时问题最大。

**2. 奖励落到句子上，而不是整段一个分。** 整段打分时，第一句错了扣得狠，后面再错几句几乎不多扣；10 句的回答错一句，分数还比 5 句的高。我先改了整段公式，没用；真正有效的是把负的优势值只加在出错那一句的 token 上。

**3. critic 升级后接着训，不推倒重来。** 从上一轮 GRPO 模型接着训 100 步，比从 SFT 重训 200 步好。

**4. 只补“critic 拿不准 + 类型对口 + 核实过”的样本。** 备选是加大量数据、随机加合成样本、只加确认是真错的样本，三种都试了，都没用。

**5. 造错的奖励：要难，但不奖励“骗过 critic”。** 最早奖励生成器造 critic 判不出的错，结果造出来的只有 24% 是真错：最容易骗过 critic 的“错误”，就是根本没错的句子。现在是先过两道门槛（是真错、读着自然），再按 critic 分数给难度分：0.3–0.5 最高，0.9 以上给 0，不设保底。

**6. 造出来的难样本，用“排序 + 人工核实”来验，不用硬门槛。** 起初用另一个 2B 模型判断是不是真错，要求概率 ≥ 0.9。后来发现，critic 看不见的地方，这个同为 2B 的验证模型也看不见。放宽到 ≥ 0.5、按分数排序后交人核实，候选多了约 6 倍，真错率从 79% 只降到 66%。

## 核心结果

所有对比都是配对的（同一批原文、同一种子重新生成），区间是按原文聚类 bootstrap 的 90% 区间。RAG 这边用 9B 金标 critic 打分，它只用来评测，从不进奖励。

**奖励粒度**（各训 50 步，200 条配对回答）：只改整段公式（R1）几乎没变化，把信号落到句子上（R2/R3）才拉开差距。

| 奖励 | 含明显错的回答 | 每条回答的明显错句 | 相对 R0 |
| --- | --- | --- | --- |
| R0 整段一个分 | 30.0% | 0.485 | — |
| R1 整段，去底噪 + 按错句计数 | 32.5% | 0.445 | −0.040 [−0.117, +0.031] |
| R2 加句子层优势 | 24.0% | 0.340 | −0.145 [−0.236, −0.061] |
| R3 再往前传一句 | 23.0% | 0.275 | −0.210 [−0.309, −0.120] |

**分段训练**（595 条配对回答）：同样用新 critic，接着训比重新训少 5.0 个点含明显错的回答 [−7.6, −2.3]。

| RAG 模型 | 含明显错的回答 | 拒答 |
| --- | --- | --- |
| SFT | 25.2% | 27.6% |
| 第一段 GRPO（200 步） | 9.8% | 6.0% |
| 新 critic，从 SFT 重新训 200 步 | 11.6% | 5.9% |
| 新 critic，从第一段接着训 100 步 | **6.6%** | 3.5% |

**闭环转了一圈，RAG 继续变好**（595 条配对回答）：按类型找到 critic 的盲区，造样本、人工核实后补进 critic，再用它从上一段 RAG 模型接着训 100 步。和自己的起点比，含明显错的回答少了 2.9 个点 [−5.5, −0.5]，含任意错（包括细微错）少了 4.7 个点 [−7.8, −1.9]，句数和长度不变，没有钻空子。

| RAG 模型 | 含明显错的回答 | 含任意错的回答 |
| --- | --- | --- |
| SFT | 25.2% | 35.8% |
| 第 1 段强化 | 9.8% | 21.7% |
| 第 2 段强化 | 6.6% | 16.8% |
| **第 3 段：用补过盲区的 critic（第一轮闭环）** | **4.7%** | **10.4%** |

有意思的是，这个 critic 自己的静态指标几乎没变（AUC −0.012，不显著），当奖励却明显有效。我的理解是：补了盲区后，critic 对细微错“有了感觉”，分数哪怕没过 0.5，在 GRPO 的组内比较里也会变成梯度。所以判断 critic 好坏，要看它当奖励的效果，不能只看静态 AUC。

**会不会只是多训了 100 步？** 我补了一个对照：同样从第 2 段出发、同样再训 100 步，只是奖励模型不换。它没有任何改善（含明显错 6.7% → 7.9%，不显著），句数还从 3.72 掉到 3.44，开始合并句子去讨好已经被摸透的旧 critic。而换了新 critic 的那组，比它少 3.2 个点含明显错 [−5.3, −1.2]、少 4.0 个点含任意错 [−6.6, −1.5]。所以提升来自补过盲区的新 critic，不是步数。

**critic 补什么数据**（Claude 金标，2061 句，其中明显错 179 句）：随机加、只加真错都没用，加 critic 拿不准的真错才有用。

| 加了什么（底座 4604 条） | 明显错 AUC | 变化 |
| --- | --- | --- |
| 不加 | 0.843 | — |
| 随机合成样本 733 条 | 0.842 | −0.001 [−0.015, +0.011] |
| Claude 确认是真错的合成样本 811 条 | 0.833 | −0.010 [−0.025, +0.004] |
| critic 拿不准、且核实为真错的 581 条 | **0.872** | **+0.029 [+0.015, +0.044]** |

**定向补一个类型**：只给最弱的“范围偏移”补 285 条核实过的样本，这一类 AUC +0.030 [+0.010, +0.052]；同样的样本不核实，只有 +0.007，不显著。

**难样本能不能造出来**：在 critic 拿不准、又读着自然的候选里，每种类型抽 10 条交 Claude，66% 是真错，而且集中在 critic 最弱的范围偏移、张冠李戴、近义偏移。结论是：模型能造出 critic 的盲区样本，瓶颈在验证。

## 失败和教训

错误合成（让生成器把正确的句子改错，用来扩充 critic）是踩坑最多的地方。几个印象最深的：

- **奖励“骗过 critic”，造出一堆不是错的错。** 只有 24% 是真错。这让我意识到，把“骗过评判者”当优化目标，等于在对抗性地挑标签噪声。
- **验证模型和 critic 一起“瞎”。** 验证模型知道改了哪里，按理更容易判断。但“知道改了哪个词”只解决定位，“原文到底支不支持”这一步它和 critic 一样吃力。把逐词改动明确告诉它，也完全没帮助。
- **生成器写的解释大多是错的，还会带偏验证模型。** 去掉解释后，验证反而更准。
- **换 9B 生成器没用**：解释变好了，但造出真错的比例一样。
- **给“过门槛”加一点保底分，生成器就往明显错的方向跑**：critic ≥ 0.9 的比例从 55% 涨到 72%。
- **用更好的 critic 接着训 RAG，结果变差**：RAG 学会了写长句躲 critic。补了长句样本后堵住了，但那只是防守。
- **拒绝采样 SFT 几乎不降幻觉**，只是拒答少了；反而“让 Claude 改对再 SFT”一次，效果差不多等于 GRPO 50 步。

贯穿这些失败的一条线是：**任何被优化的目标都会被钻空子，而评判者和被评者越相似，空子越难发现。** 所以最后我把人工核实放在闭环里唯一一个关键位置：样本进 critic 之前。

## 还没解决的，和下一步

- **还没有系统化的错误体系。** 现在只有 9 个机制类。critic 真正漏掉的显然错，往往是更细的模式：限定词丢失、角色颠倒、事件错配、时间视角错位。下一步要建一套分层体系（粗类 → 机制 → 子类），子类从真实错误里归纳；每个子类有定义、正反例、适用条件、造法、核实要点和样本库，并用它来驱动评测、补样本和生成器出题。
- **还没有在其他任务上验证。** 只在 RAGTruth 的问答和摘要、用 2B 模型做过。智能搜索（多来源、噪声大、来源互相矛盾）和 Agent（多步工具调用轨迹）还没碰；critic 的输入形式和错误体系都需要扩展。
- **指定错误类型，生成器还是不遵守。** 要求的类型和实际造出的只有约 31% 一致。原因不在生成器，而在很多句子本来就不适合这类错：一句话里没有数字，就造不出数字错误。需要一个"适合度"模型，先在大批句子里挑出适合改写的（句子，类型）组合，只在合适的句子上改写，而不是每句都改。第一版用规则，之后用生成成功率的数据训模型。
- **现有造样本方式接近饱和。** 生成器迭代四轮，难样本一直停在每 2048 条约 40 条；"和原文高度重合、只改一处"的显然错盲区，自由改写基本造不出来。
- **人工核实最贵。** 难段里只有约一半是真错；对照实验证明不核实会拖累整体。
- **评测的局限。** Claude 代替人工，和真人的一致性没测过；评测用的 9B critic 和被测的 2B 可能有相似偏差；没有做多种子重复。
- **还在验证中。** 第二轮闭环的结果还没出来：第二轮 critic 的静态区分度不升反降，要看用它接着训 RAG 的效果。

## 工程和复现

整个闭环都在单张 RTX 5090 上跑通。几个让它跑得动的关键处理：

- **GRPO 训练侧共享前缀**：同一个提示的 16 或 32 个回答只算一次前缀，单卡就能同时放训练和推理。
- **生成和打分流水线并发**：策略和几个打分模型以 LoRA 形式挂在同一个 vLLM 上。
- **打分模型统一成“单字母选项 + 温度校准”**：一次前向就出校准过的概率。16 个 critic 一起挂上混合打分，比一个一个打快约 8 倍。
- **可复现**：所有运行固定种子，重跑得到同样的数据；每次实验都记在实验日志里，包括踩过的坑。

不需要 GPU 就能看到主要结果：

```bash
pip install -r requirements.txt && pip install -e .
python -m scripts.demo_tables   # 重新算出文中的对比表
python -m pytest -q             # 134 个单测
```

有 GPU 的话，`requirements-gpu.txt` 里是训练机上的实际版本，完整闭环的分步脚本在仓库的 README 和 `scripts/remote/` 里。

## 几个常被问到的问题

**用 Claude 当标注和评测，会不会自己评自己？** 训练和评测里都不调 Claude。它只在两处出现：构建数据（改对、核实）和最终验收的金标。RAG 的评测用的是另外训的 9B critic，它也从不进奖励。但 Claude 和真人的一致性确实没测，这是我认为最需要补的一项。

**分段训练更好，会不会只是因为训得更久？** 有这个混杂：分段共 300 步，重新训是 200 步。但重新训那组从第 100 步到第 200 步已经不降了（−0.010，不显著），所以差距不太可能只是步数带来的。

**为什么不直接用大模型当 critic？** 要当 RL 奖励，就得便宜、快、能逐句给校准过的概率。2B 单字母打分一次前向就够。大模型更适合放在数据核实和验收这两个不频繁的环节。

**为什么不做多种子重复？** 算力有限，我把资源给了更多的对照组。所有对比都是配对的，并按原文聚类做 bootstrap；同一检查点重复生成的差异大约 1–1.5 个点，文中的主要结论都超过这个幅度。

**如果重做一遍，会怎么安排？** 会更早地按类型分析 critic 的盲区，而不是先大量造数据再发现没用；也会更早把“验证”当成和“生成”同等重要的问题来设计。
